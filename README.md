# Geo Layers Control

Тестовое задание: интерфейс управления картографическими слоями (температура, ветер, инсоляция)
на **React 19 + TypeScript + [vedro](https://www.npmjs.com/package/vedro)**, с настоящей картой на
MapLibre GL.

Для каждого слоя:

- включение / выключение;
- прозрачность (opacity);
- статус `idle / loading / success / error`;
- повторная загрузка после ошибки;
- при включении — запрос к mock API со случайной задержкой и случайными ошибками.

Дополнительно: групповые действия («Включить все», «Выключить все», «Повторить ошибки»), панель
настройки mock API (процент ошибок, задержка) и стресс-режим `?layers=150`.

## Запуск

```bash
yarn install
yarn dev          # http://localhost:5173
yarn test         # vitest
yarn validate     # typecheck + eslint + prettier + tests
yarn build
```

Стресс-режим: открыть `/?layers=150` (можно любое число до 1000).

Стек: React 19, TypeScript (strict), Vite, styled-components, vedro, MapLibre GL, Vitest +
Testing Library, ESLint (typescript-eslint `strictTypeChecked`) + Prettier + Husky/lint-staged,
Yarn, GitHub Actions.

## Архитектура

```
src/
├── app/                       композиция: провайдеры, раскладка, конфиг из URL
├── shared/                    утилиты без доменной логики (abort, PRNG, ui-примитивы, тема)
└── modules/layers/            модуль «слои», наружу — только через index.ts
    ├── domain/                чистые типы и логика: LayerDefinition, LayerState, реестр, opacity
    ├── api/                   граница с backend: интерфейс LayersApi + mock-реализация
    ├── store/                 vedro-store, селекторы, хуки подписки, провайдер
    ├── services/              LayersController — вся бизнес-логика и асинхронность
    ├── map/                   синхронизация store → MapLibre (вне React)
    └── ui/                    React-компоненты
```

Поток данных однонаправленный:

```
UI (onChange) ──▶ LayersController ──▶ LayersApi (mock)
                        │  dispatch
                        ▼
                  vedro store ──store.on(id)──▶ UI-компоненты (useSyncExternalStore)
                        │
                        └──────store.on(id)──▶ bindLayersToMap ──▶ MapLibre
```

Разделение ответственности:

| Слой       | Знает о                        | Не знает о                   |
| ---------- | ------------------------------ | ---------------------------- |
| `domain`   | только о себе                  | React, vedro, MapLibre, сети |
| `api`      | domain                         | store, UI                    |
| `services` | domain, api (интерфейс), store | React, MapLibre              |
| `store`    | domain, vedro                  | api, MapLibre                |
| `map`      | domain, store                  | React-компонентах, api       |
| `ui`       | хуки store, controller         | api, vedro API напрямую      |

- **Компоненты не делают `dispatch`**, а вызывают методы `LayersController`
  (`setEnabled`, `setOpacity`, `retry`, `setAllEnabled`, `retryFailed`). Controller —
  единственное место, где меняется состояние и живёт асинхронность. Его легко тестировать без
  React.
- **API — интерфейс** (`LayersApi`). Mock подменяется на реальный REST-клиент без изменений в
  остальном коде. В тестах используется управляемый `createDeferredApi`.
- **Карта — не React-компонент, отрисовывающий слои.** `MapView` рендерится один раз, а
  `bindLayersToMap` императивно синхронизирует store с MapLibre. Смена прозрачности меняет
  только `setPaintProperty` одного слоя, React в этом не участвует.
- **Тяжёлые данные вне реактивного store.** GeoJSON лежит в `LayerDataCache` (`Map`), в store —
  только лёгкое сериализуемое UI-состояние. vedro сравнивает значения через `JSON.stringify`,
  поэтому класть в него мегабайты GeoJSON нельзя.

## Управление состоянием в vedro

### Форма store: каждый слой — отдельный ключ

```ts
type LayersState = Partial<Record<LayerId, LayerState>>;

interface LayerState {
  enabled: boolean;
  opacity: number;
  request:
    | { status: 'idle' }
    | { status: 'loading'; requestId: number }
    | { status: 'success'; requestId: number; loadedAt: number }
    | { status: 'error'; requestId: number; message: string };
}
```

У vedro есть подписка на конкретный ключ: `store.on(key, cb)`. Поскольку каждый слой — это
ключ верхнего уровня, компонент или биндинг карты подписывается ровно на свой слой. Обновление
слоя уведомляет только его подписчиков, то есть стоит **O(1), а не O(N)** по числу слоёв.

`request` — discriminated union: невозможные состояния (ошибка без сообщения, success во время
загрузки) не выражаются типами.

### Какие части vedro используются и почему

Перед реализацией я прочитал исходники vedro 1.1.0 (`node_modules/vedro/lib`). Документации
мало, а поведение `useSelector` определяет количество рендеров. Находки:

| #   | Поведение vedro 1.1.0                                                                                                                                                            | Что с этим сделано                                                                                                        |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| 1   | `useSelector` подписывается на **весь** state (`@state`): каждый `dispatch` вызывает каждый селектор дважды и делает `JSON.stringify` → O(N) на обновление                       | для строк слоёв свой хук `useLayerSelector` = `useSyncExternalStore` + `store.on(id)` → O(1)                              |
| 2   | селектор захватывается один раз (`useEffect(..., [])`) — если он зависит от пропсов (`id`), после их смены хук продолжит читать старые данные                                    | в `useLayerSelector` подписка пересоздаётся при смене `id`                                                                |
| 3   | начальное значение берётся в render, а подписка — в `useEffect`: обновление между ними теряется; нет `useSyncExternalStore` → возможен tearing в concurrent-режиме               | `useSyncExternalStore` решает обе проблемы; монтирование не вызывает `dispatch`                                           |
| 4   | `isAsyncFunction` проверяет `fn instanceof Promise`, что для функции всегда `false`: **async-callback уходит в синхронную ветку, и возвращённый им `Partial<S>` молча теряется** | async-колбэки в `dispatch` не используются; асинхронность — в `LayersController`, в store пишутся только готовые значения |
| 5   | `dispatch(object)` бросает ошибку, если в объекте есть ключ, которого нет в state; `dispatch(key, undefined)` тоже бросает                                                       | все ключи создаются при инициализации из реестра, значения никогда не `undefined` (`status: 'idle'` вместо пустоты)       |
| 6   | `useDispatch()` возвращает новую функцию на каждый render — она ломает `memo`, если передавать её пропсом                                                                        | компоненты получают стабильный `controller` из контекста                                                                  |
| 7   | `store.get()` без ключа копирует весь state                                                                                                                                      | горячий путь использует только `store.get(id)`                                                                            |

Что используется из vedro:

- `createVedro` → `Provider` (свой store на каждый провайдер, без module-level синглтона, тесты
  изолированы) и `useStore`;
- `store.dispatch(key, value)` для одного слоя и `store.dispatch(partial)` для групповых операций:
  «Включить все» для 150 слоёв — **один** dispatch и одно уведомление `@state`-подписчиков;
- `store.on(id)` — точечные подписки для UI и карты;
- `useSelector` — там, где он уместен: `LayersSummaryBar` («включено X из N»). Это агрегат по
  всем слоям, подписчик один, пропсов нет, результат сравнивается структурно, поэтому компонент
  перерисовывается только при изменении счётчиков.

## Асинхронность и гонки

`LayersController.startRequest` защищает от гонок двумя независимыми механизмами:

1. **AbortController** — при выключении или повторном включении предыдущий запрос отменяется
   (mock API честно снимает таймер).
2. **Монотонный `requestId`** — ответ применяется, только если он принадлежит последнему
   запросу этого слоя. Это гарантирует корректность, даже если транспорт проигнорирует
   `AbortSignal`. Тестовый API специально его игнорирует.

Сценарии, покрытые тестами (`layersController.test.ts`):

- вкл → выкл → вкл, где первый (медленный) ответ приходит после второго: побеждает второй;
- устаревшая **ошибка** не перетирает свежий успех;
- ответ, пришедший после выключения слоя, отбрасывается, кэш не заполняется;
- 11 быстрых переключений подряд, ответы в обратном порядке: применён только последний, все
  предыдущие отменены;
- повторный `setEnabled(true)` не делает второй запрос;
- `dispose` при размонтировании отменяет всё. Controller не хранит флаг «disposed», поэтому
  StrictMode (mount → unmount → mount) ничего не ломает.

Порядок отрисовки слоёв на карте тоже защищён от гонок: слой вставляется под следующий видимый
слой из реестра (`beforeId`), поэтому итоговый порядок не зависит от того, чей ответ пришёл
первым.

## Отсутствие лишних render

- `LayerRow` ни на что не подписан и после монтирования не перерисовывается. Его дети
  подписаны каждый на одно поле одного слоя: `LayerToggle` → `enabled`,
  `OpacitySlider` → `opacity`, `LayerStatus` → `request`.
- Селекторы возвращают примитивы или ссылки, уже лежащие в state, поэтому
  `useSyncExternalStore` сравнивает их через `Object.is` без аллокаций.
- Контекст с зависимостями (`controller`, `registry`, `store`) создаётся один раз и никогда не
  меняется, поэтому не вызывает рендеров.
- Карта обновляется в обход React.

Это проверяется тестами через `React.Profiler` (`LayerPanel.test.tsx`):

- при 150 слоях включение одного слоя и его загрузка вызывают коммит **только** в строке этого
  слоя;
- движение слайдера прозрачности перерисовывает только слайдер, но не переключатель и не статус.

Тест проверен «мутацией»: если подписать компонент на весь state, он падает (150 коммитов вместо
одного).

## Масштабирование с 5 до 100+ слоёв

- Новый слой — одна запись в реестре (`LayerDefinition`). Новый **тип** слоя — стиль в
  `LAYER_STYLES` и генератор в mock API. Остальной код не меняется.
- Стоимость обновления слоя не зависит от числа слоёв (точечные подписки, O(1)).
- Групповые операции делаются одним `dispatch`.
- MapLibre (~1 МБ) грузится отдельным lazy-чанком, панель интерактивна сразу.
- Проверено в браузере на `?layers=150`: «Включить все» (150 параллельных запросов) и движение
  слайдера работают без подвисаний.

Что бы я сделал дальше для 1000+ слоёв и реальных данных:

- виртуализация списка (`react-window` / `@tanstack/react-virtual`), так как DOM на 1000 строк
  уже заметен;
- ограничение параллельных запросов (пул на ~6 запросов) и retry с backoff;
- кэш с TTL / stale-while-revalidate вместо удаления данных при выключении слоя;
- вместо GeoJSON — vector/raster tiles (MVT, WMTS) с backend, парсинг тяжёлых данных в Web Worker;
- поиск и группировка слоёв в панели, сохранение состояния слоёв в URL.

## Строгая типизация

- `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`,
  `noPropertyAccessFromIndexSignature`, `useUnknownInCatchVariables`;
- ESLint `strictTypeChecked` + `no-explicit-any: error`. В коде приложения нет `any` и нет
  приведений типов через `as` (кроме `as const`); единственный каст — в тестовом фейке карты,
  с комментарием;
- `LayersState` объявлен как `Partial<Record<...>>`: vedro типизирует `get(key)` как всегда
  определённое значение, но для динамических id это неправда. Тип честно заставляет обработать
  отсутствие слоя (`getLayerState`).

32 теста (Vitest + Testing Library):

- `services/layersController.test.ts` — жизненный цикл, ошибки, retry, гонки, групповые операции;
- `api/mockLayersApi.test.ts` — задержка, ошибки, отмена через `AbortSignal` (на fake timers);
- `map/bindLayersToMap.test.ts` — синхронизация с картой через фейковый `MapLike`, порядок слоёв;

## AI-инструменты

Использовал **Claude Code** (агент в терминале и в облачной сессии, связанной с GitHub).

- **Исследование незнакомой библиотеки.** Про vedro почти нет информации, поэтому я попросил
  Claude Code скачать пакет и разобрать исходники `lib/`. Так нашлись особенности из таблицы
  выше, в том числе баг с async-dispatch (`instanceof Promise`). Вывод об архитектуре (ключ на
  слой + `store.on(id)` + `useSyncExternalStore`) сделан по этому разбору.
- **Проектирование.** Обсуждал варианты формы store (один ключ `layers` против ключа на слой),
  где держать GeoJSON и как защищаться от гонок (только abort, только токен или оба).
- **Генерация кода и конфигурации.** Скаффолдинг Vite/TS/ESLint/Prettier/Husky, реализация
  модулей по согласованной архитектуре, тесты. Весь код прошёл ревью и правки.
- **Проверка тестов.** Попросил сломать код намеренно (подписать компонент на весь state) и
  убедиться, что тест на изоляцию рендеров действительно падает.
- **Диагностика.** Claude Code запускал production-сборку в headless Chromium (Playwright) и
  нашёл две проблемы, которые не видны в unit-тестах:
  1. MapLibre v6 ищет web worker относительно своего модуля, а после бандлинга файла там нет →
     воркер собирается Vite через `?worker&url` и передаётся в `setWorkerUrl`;
  2. `maplibre-gl.css` ставит контейнеру `position: relative` и перебивает стили → контейнер
     получал нулевую высоту.
- **Нагрузочная проверка.** Скрипт в Playwright на `?layers=150`: включить все, подвигать
  слайдер, проверить итоговые счётчики.
- **Ревью.** Отдельный проход по диффу: гонки, лишние подписки, `any`/касты, утечки
  (отписки, `map.remove()`, отмена запросов при размонтировании).
